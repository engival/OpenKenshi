## Regional weather (stages 1 and 2, 2026-10-30)

Data chain, all read from the merged game data plus one map file; no exe knowledge needed:

- `data/newland/land/areasmap.tga` (256^2, 1152 world units per cell, bottom-left origin, flipped on load so row 0 = north): pixel colour 0xRRGGBB == `BIOME_GROUP.index` (TERRAIN_FORMAT.md; checked: the Deadlands spawn lands in the Deadlands group, Sho-Battai in The Great Desert, the Shark lake in The Swamp).
- `BIOME_GROUP.seasons` refs: v0 = order, v1 = relative duration. `SEASON.weathers` refs: v0 = probability, v1/v2 = min/max duration in minutes (`fcs.def`). 74 groups, 71 colours used by the map; 8 groups (Central, Arm of Okran, Rebirth, Obedience, Berserker Country, Empire, Watcher's Rim and the unnamed ocean colour 000000) have no seasons or no weathers.
- **Representative weather rule** (`representativeWeather()` in `weathermap.cpp`, the one function a sim snapshot replaces): default season = the longest duration (ties: lower order, then list order); weather = the highest probability in it (ties: list order); no season / no weather = the default `SkyWeather` (clouds 0.25, no fog). Examples: Desert -> Desert Blasts -> Desert Blaster; Deadlands -> `deadlands` -> Heavy_Rain deadlands (clouds 1.0, rain 100, no fog); Skinner's Roam -> Dust Storm Approach -> Sand stream; 74 groups -> 23 distinct weathers. `KWEATHERLOG=1` prints the whole table.
- Stage 1 (`WeatherMap::blend`): a 9x9 Gaussian stencil of areasmap cells around the camera (`--weather-blur KM`, default 1 = full width at half maximum) gives a weight per weather; `SkyWeather::blend` mixes wind speed, heat haze, dust and the fog (as density x colour, so a clear region does not wash out a storm's colour) linearly. The BIOMES sun/ambient (`ambientmap.png`) is averaged over the same stencil. The HUD shows `weather auto: Clear 70% / Dust Storm 30%` (top three, >= 1 %).
- **Sky ramp (2026-11-10, kenshi-k16.2.68; the exe's rule, kenshi-inspect findings/sky_cloud_density_static.md).** Sky colour mult and cloud density are not blended: `SkyRamp` (sky.hpp) holds one pair for the sky, fed only by the camera group's current record (raw, not x strength). A new record there or entering another group starts a linear 30 s ramp from the current value in game-speed seconds (frozen while paused); a camera jump over 89 u in one frame into another group snaps. Ours snaps on the first frame (the exe starts from the save or 0.25), and scene tests always snap. `dump sky` prints the pair and the group.
- Stage 2: a 256^2 RGBA16F texture (rgb = fog colour x density x 1e4, a = density x 1e4, premultiplied) blurred with a Gaussian (`--front-blur KM` sigma, default 2) and sampled bilinearly in the terrain, building/foliage and water fragment shaders (`fog_map`, `light_finish` in `lighting.inc`). Since 2026-10-31 it is averaged over 4 midpoints of the camera-to-fragment ray (`FOG_MAP_RAY`), i.e. the ray's mean density and density-weighted colour: a region's fog counts only for the part of the ray inside it. Before, a ridge just inside Skinner's Roam (Sand stream dust) took its full fog 24 km out from greenlands_bridge, a beige wall the live shot does not have. Both paths share one fog colour rule: raw colour x max(sun alpha, nadirLight), scene referred (no exposure, no gamma; the composite exposes once, k16.2.81). `Sky::regionalFog` selects the map; a manual weather uses the uniform fog.
- Manual weather pins the blend off: `--weather NAME`, a scene's `weather=NAME|default`, `set weather`, and `,` / `.` (the ring is auto, default, then WEATHER records). `--weather auto` / `weather=auto` / no `--weather` = regional. Existing scenes keep `weather=default` (pinned), so their pixels do not change; the three new ones are `weather=auto`.
- **Storm haze (client extension, mine).** Most weathers have `fog enabled = 0`, including the Deadlands' and the dust storm records, so the data alone gives no wall. The exe does darken the horizon with cloud density (SKY_EXE C35, LIGHTING_EXE Q6 `horizonClouds`: colour x (1 - pow(sat(d - 0.5), 0.3)), weight sat(1.4 d - 0.3)). `SkyWeather::stormDark` = that product (0 for d <= 0.5, 0.81 at d = 1). It scales the atmosphere fog colour by (1 - stormDark) (this also darkens the sky horizon, like the exe's horizon colour) and, where the record's fog is off, becomes a global haze of density stormDark / 20000 (`kStormHazeDistance`, tunable) in colour (1 - stormDark). Clear weathers are untouched. So a Heavy_Rain / dust-storm region fades into a dark grey wall from about 5 km out and dominates at 15 km+.
- Carried and blended but not rendered: heat haze, dust (no post effect or surface coat yet).
- **Live weather (sim WEATHER 41, 2026-11-01; `WeatherMap::setLive`, rules in `reference/WEATHER_CYCLE_LIVE.md`).** With a sim link, each BIOME_GROUP shows the sim's current weather instead of the representative one (the atlas now holds one `SkyWeather` per group, `groupWeather`; cells map to groups). Per group:
  - fog (the effective density and colour after `finalize`, so the cloud haze too) lerps from `previous` by `fogBlend`;
  - sky colour mult and cloud density are the record's; the sky ramp eases them (above), so the wire's `skyBlend` is not used;
  - rain, wetness, dust, dust inside, heat haze and the effect amounts are the current weather's x `strength` (no cross-fade, as the exe).
  - wind speed = lerp(`wind speed min`, `wind speed max`, `strength`) (1409dcf60); it drives the rain / dust drift and the wind sound's Intensity. Without a sim the representative weather keeps `wind speed max`. The cloud scroll still uses the SkyX default (1, 1).
  - The fog map is rebuilt (CPU blur, new image) when a group's fog changed: about 1 Hz during a fog fade, otherwise only on a pick.
  - The camera blend is unchanged (our Gaussian, not the exe's 4-sample rule). `KWEATHERLOG=1` prints each live change.
  - Checked live against the weather server build (`cpp/build-weather`, 6a07516): 66 regions, 29 groups changed from their representative weather on the first frame, e.g. Border Zone -> Sand stream at strength 0.64. Fades checked on cpp/build (7472341) with `set simspeed 64` for 10 s, then 1: 82 live picks, fogBlend values 0.41..0.99 (many groups share a value: a season change starts them on one tick), skyBlend ramping about 0.033 / s at speed 1 (30 s).
- Stage 3 (clouds, sun and ambient per world position, exposure-only camera adaptation) is not started.

Open questions (not decidable from the data files):

## Particles (2026-10-31)

Weather particle effects, first pass: rain and the sand stream. Own code (`src/particles.{hpp,cpp}`, `shaders/particles.glsl`); the ParticleUniverse `.pu` format was read from its public documentation (ParticleUniverse plugin manual, Henry van Bakel, MIT) and is credited here; nothing is copied.

What the game does (all under `data/`):

- Chain: WEATHER `effects` refs (target, v0..v2 = a count and a time range, not decoded) -> EFFECT (`particle system`, `type`, `wind affected`, `ground colour`, `colour multiplier`) -> `particles/scripts/<name>.pu` -> `particles/materials/*.material` -> `particles/textures/*.dds`. rebirth.mod overrides some EFFECT records (Kenshi_Heavy_Rain becomes type 5, Desert Blaster lists Sand-Stream), so only the merged data tells.
- Rain: `Kenshi_Heavy_Rain.pu` (`_red`: material `Kenshi_rain_basic_red`). One Box emitter, 6400 / s, ttl 0.3-1 s, velocity 90-182, direction (0.2,-1,0), spread 1 deg, box 120 x 120 x 100 about (0,15,0) of the camera node, `oriented_self` billboards 0.85 x 4 with `bottom_center` origin, colour 0.32 grey, an OnPosition observer expiring particles below y -5.85. Material `Kenshi_rain_basic`: `Kenshi_Rain_Basic.dds` (256 x 1024 streak, BC1), `scene_blend add`, depth write off, `Basic_Coloured_Ambient_VP` + `Basic_Texture_Clipped_FP_HLSL`.
- Particle shader (`materials/forward/basic.hlsl`, traced): out = texture x vertex colour; vertex colour = script colour x `clamp(5 sunDirection.y + 0.2, 0.1, 1)`. **No sun colour, no sky light, no fog.** So the dust billboards are not what makes the game's shadowed faces red (LIGHTING.md section 12): at dawn they are x0.2 and alpha <= 0.13. The interior mask clip (second texture unit): done, 3f796c8c (rain inside the Storm House hull is dropped, rain outside its wall drawn; verified headless 2026-11-10).
- Dust: `Sand-Stream.pu` (material `Sand-Wisp`, alpha blend, 900 particles, system scale 14, Scale and Colour affectors, alpha <= 0.13); `Permanent-dust-storm.pu` and `DesertCloudStorm.pu` use the same machinery (Circle emitters, DustMite materials) and parse, but are not enabled.
- Strength: `rain intensity` / 100 scales the rain emission (the exe: rain = intensity x effect strength, WEATHER_LIGHT_EXE). `SkyWeather::effects` carries the amounts and is blended like the other fields (regional weather mixes by weight).

What kclient does:

- A parser for the .pu subset (Billboard renderer, Box / Circle emitters, dyn_random / curved / oscillate values, Colour / Scale / TextureRotator / LinearForce affectors, OnPosition ground kill) and a CPU simulation (rain about 3500-4000 live, `mt19937`). Camera-local emitter: particles are born in the box around the camera and stay in world space; the kill plane is the terrain height under the camera - 5.85. Wind affected systems drift by the weather wind.
- One transient instance buffer, instanced quads, own pass after the fog volumes (`Hdr::particlePass`, scene colour LOAD, no depth attachment): the fragment samples the scene depth like `fogvolume.glsl` and drops what lies behind. Additive (rain) and alpha (dust) pipelines; alpha particles are sorted far to near and fade over 60 units in front of the scene (the game intersects hard). Colour x ambient factor x baked exposure, linear.
- Determinism: a new system is pre-warmed (its longest lifetime, 0.05 s steps), scripted runs then freeze the simulation (dt 0); seed 1 at every scene apply. Interactive runs simulate with the real dt.
- Scene keys `rain=A` (replaces the weather's rain with Kenshi_Heavy_Rain at strength A) and `dust=A` (adds a Sand-Stream around the camera); `--no-particles`. In scenes.txt: petal_hills, obsidian_pool, grass_point_rain rain=0.8, dust_red_dawn dust=0.5. The screenshot log prints the active systems.
- Only rain is drawn from a weather's own list (so deadlands_inside and swamp_noon_rain now rain). Sand streams are not: their placement (count / time range in the effects refs, wandering speed 400) is not decoded, and the merged Desert Blaster / Sand stream weathers would haze every scene.

Result: rain streaks match the live petal_hills shot in length, slant, density and brightness (very faint: 0.32 x texture x exposure). dust_red_dawn with dust 0.5: soft wisps, 13 % of pixels change by about 1 level on average, no red shift (confirms the traced shader). GPU (RX 7900 XTX, 1280x720, `--scene-frames 40`): rain 0.00-0.01 ms (about 3000 instances), dust 0.03 ms (364). CPU not measured separately.

Open: Scale affector semantics (growth per second vs absolute factor, abscissa age vs life, system scale on the rates) are MINE: `kGrowth` = 4 in `particles.cpp`, Sand-Stream wisps are 100s of units across; an absolute reading gives 15 km veils. `ground colour` (sand taking the terrain colour) and EFFECT `colour multiplier` are unused. Not ported: splashes (DoPlacementParticle), mist, ash, tornado, blood, EFFECT instance placement (the psys itself, though: the weather's Lightning_Bolt runs as a placed system since k16.2.11, W2e).

New .pu features (kenshi-k16.2.102.1, 'lightning storm' = `kenshi_lightning_beam2`, the WEATHER of that name refs it as a type 7 effect, ref 10/1/5; spawned by the same `WeatherInstances::spawnBolt` as Lightning_Bolt):
- **Line emitter** (`end`, `min_increment`, `max_increment`, `max_deviation`): each particle is born one random increment further along the segment emitter position -> `end` (back to the start past the end), shaken by up to `max_deviation` on every axis. The deviation draw (uniform per axis) is MINE, the exe's is not traced.
- **Align affector** (`resize`): a particle's long axis points at the previous particle of the pool (the one emitted before it); `resize` sets its height to that distance. The pool's first particle keeps the world up axis. Because successive sweeps of the line follow each other in the pool, the first particle of a sweep links back to the top of the last one: a long straight streak along the beam, the bright core of the shot. MINE (PU's list order and the Align neighbour choice are from its manual, not the exe).
- **`billboard_type oriented_shape`**: the quad is not turned to the camera; it lies in the plane of the particle's own orientation (Ogre BBT_ORIENTED_SHAPE). The orientation is the shortest turn of up onto the Align direction (`particles.glsl`, instance float 15 `shape`). Seen edge-on a beam is thin, as in the original's model; MINE for the x axis choice.
- The other two techniques of the script (dust: Line + SphereSurface emitters; flash: Point emitter, vertex rotation, Scale) ran on the existing code. Shots: `findings/kenshi-k16.2.102.1/`; `debug weff kenshi_lightning_beam2 0 -450` pins one (forward at yaw 0 is -z).

## Characters (2026-10-31)

Plan (agreed with the user): shared `.skeleton` reader -> skinned bodies -> assembly (heads, hair, armour, weapons) -> locomotion -> combat clips from sim state; the character creation screen later. The sim (kenshi-b0) will own timing, root motion and hits; the client plays clips.

Done (`src/characters.{hpp,cpp}`, `shaders/character.glsl`; `--character SPEC`, repeatable):
- Skeleton and clips: `kworld/ogreskeleton.hpp` (shared with the sim). Every human clip has all 30 tracks; layering will happen at blend time.
- Skinning like `skin.hlsl` main_vs: 3 weights, 60 bones, a 3x4 matrix per bone in a uniform array, the w divide. Gotcha: `SG_VERTEXFORMAT_UBYTE4` is an integer attribute in sokol GL (`glVertexAttribIPointer`), so the shader declares `uvec4`. The meshes carry no binormal: cross(t, n) x t.w, as in severed_limb_vs.
- Body: `character.hlsl` main_fs. The RACE body set and the HEAD set share one mesh (the head at uv.y + 1, border colour 0). Skin tone: `body *= 1 - skintone x mask`; the skintone = 1 - the editor's "Skin Tone" colour, which is NOT TRACED. Glow from headMask.g. DARKEN 0.7.
- Shirts: ARMOUR `vest texture` / `vest normalmap` in the vest slots. With no shirt, the vest normal is bound to nothing.dds, because its alpha is coverage.
- Armour meshes: `skin.hlsl` main_fs. The ARMOUR `material` ref -> MATERIAL_SPECS_CLOTHING texture / normal map; normal alpha < 0.6 cut out; green flipped; `specular mult`; diffuse mip bias -2 (Skinned material); DARKEN 0.8.
- Hair: ATTACHMENT mesh with `hair_fs`, two-sided. The channels and `alpha rejection`/255 come from the record. The colour is COLOR_DATA `color 1`; the scalp `head texture` goes into the body's hairMap.
- Shirt colour (traced, 140533b50 + character.hlsl): when the item has a resolved colour, `vest.rgb = mix(vest.rgb, color1 * mean(vest.rgb), colorMap.r)`. The colorMap is the `vest colormap`, or white.dds when that is empty. `dont colorise` clears the resolved colour (FUN_1405358a0), for armour meshes too. In gamedata.base only White Vest is colourisable, and its own `color` (white) overrides the faction's.
- Beards (`beard=`): a mesh-less ATTACHMENT. Its `head texture` is the body's beardMap, mixed after the hair in the hair colour (character.hlsl). The BeardBaseHead_0N textures hold one beard per channel, so beardAlpha is the one-hot `head channel` (NOT TRACED; `head alpha channel` is 1 on all of them, and channels 0/1/2 render three distinct beards).
- Meshes: hair/armour meshes mostly link no skeleton (48 of 417 do); their indices are already body handles. Linked ones are remapped by bone name.
- Rendering details: Ogre back-face culling (CCW front). Shadows clip the same cut-outs. Zero-tangent vertices fall back to the geometric normal: cargopants_f's waist rim made NaN, which showed white.
- `hide hair` is 1 on most items (shirts, pants), so it is honoured on head gear (slot 3) only (NOT TRACED).
- Layered clips: `anim=NAME` (repeatable) plays ANIMATION records. Each record's `delete ...` flags become a bone mask (traced bone lists:

## Locomotion fidelity (user 2026-11-06)

Goal (user): characters move in a physically believable way, never sliding or floating. Symptom: a run stops mid-stride, then morphs into
the idle; in combat bodies drift sideways.

Data (measured 2026-11-06): one 30-bone Biped skeleton per race, 174 FK clips keying every bone; no IK, constraints or contact markers.
Locomotion clips are in place. Walk has a full foot roll (heel strike toes-up ~20 deg, flat stance, heel rise, push-off on Toe0); run lands
near flat and spends most of its stance on the ball (Toe0 bends up to ~28 deg). The clip stance is clean (ankle travels back at a constant

## Ragdolls and carried bodies (client side of `docs/reference/PHYSICS.md`; planned 2026-11-06, UNPARKED 2026-11-06: body piles, ROADMAP 6b)

The original (kinspect `findings/ko_transitions.md`, `physics_engines_carry_live.md`): there are no fall or death clips. On KO or
death the character becomes its race's ragdoll (`male`/`female`/`carry ragdoll` .phs) at its current position and velocity, after an
optional `Impacts` flinch (`Heavy_Hit` / `Light_Hit`). The lying pose for the whole down time IS the ragdoll. Recovery removes the
ragdoll and plays `standing up 3` (`crawl idle down` while it can't stand).
Today (interim): a lying character snaps to a frozen `crawl idle down` (simview.cpp, MINE).

- **Engine: Jolt Physics (MIT), vendored, client only.** Why not PhysX 5: Jolt is plain C++17 with CMake, has no GPU or SDK parts, its
  ragdoll and skeleton-mapper API fits our skeletons, and its deterministic mode leaves PHYSICS §5 open. Ragdoll shapes come from the
  race `.phs` (capsules, joints, limits) read at load; no hand-authored rigs.
- **Ragdoll event: APPROVED 2026-11-06 (sim kenshi-35; sim side queued, SIMLINK text with it) as EVENT kind 48: id u64, cause u8 (0 KO, 1 death, 2 drop, 3 launch), dir f32 x3, strength f32, part strid, seed u32; after event 3/5 on the same tick. While flag bit 5 is set CHAR_DYNAMIC x, y, z are the rest point, plus a trailing restYaw f32 (bit 5 set, bits 15/16 clear). Seed per KO from the sim RNG; knockback numbers OURS, UNSURE. Sim BG landed 46e9c2d5; client decodes both (`ragdoll:` log line, `dump chars` restYaw), verified live in the duel. A ragdoll exists only while KO'd or dead (a conscious crawler animates, gets no 48); a crawler KO'd sends 3 + 48 cause 0, one dying unhit cause 1; until sim BG2 lands, ignore cause 3 on a body that is neither (the original never hits an unconscious body, so launches are for later knockback). Original wish list:** id, tick, cause (KO, death, drop, launch), impulse direction (3 f32)
  and strength (f32), the hit part sid (u32, 0 = none; it picks the flinch and where the impulse lands), seed (u32). Plus the rest
  point (x, y, z and the body's head-to-feet yaw) once the sim decides it. The rest point must be **state, not only an event**: it goes
  on the down character's record, so a client that loads in late or newly gains interest gets the body where it lies, with no fall.
  A get-up needs no event; the cleared down flag plays `standing up 3` from the ragdoll's final pose.

### Loading screen responsiveness (user 2026-11-07; done k16.2.26, 2026-11-10)

- Symptom: during startup loading the X11 window stops responding (a resize does not redraw).
- Cause: sokol_app runs the X event pump and `frame()` on one thread. `frame_loading` runs one whole `app.loadSteps` step per frame
  (main.cpp, "The rest of the startup is a list of steps"), so the window freezes for as long as the longest step. All sokol/GL calls
  must stay on that thread.
- Measurement (k16.2.26): `frame()` records the wall gap between frames and the phase that did the work (the load step's name, the
  session load, the world frame). A gap over 250 ms is an evlog `stall` event (kind `stall`, which phase in its message) and a
  `kclient: stall:` line. The startup maximum prints at the first world frame, the session-load maximum when the session load ends.
- Before (headless, 1280x720, spectate_fight): startup worst 180-186 ms, but the last step hid a 3.3 s `characters` step (the game data
  merge plus the character assets); `terrain: colour map` 180 ms, `terrain: detail textures` 155 ms (upload half); session-load worst 71 ms.
- Fixed: `characters` = the game data merge on a `std::async` started in step 1 (the step polls it), the character asset build one frame,
  the panel records one job per record under a 16 ms/frame budget, and the game data freed on a worker (its destruction was ~140 ms).
  `terrain: colour map` = the cache read on a worker, the colour and alpha uploads on the main thread. `terrain: detail textures` = three
  upload frames (layer arrays / the 8192^2 overlay / the rest and the samplers), the pipelines after them. `water` = the two PNG decodes
  (the 2048^2 flowmap, ~40 ms) on a worker, the uploads in the step. The simlink hello's data hash moved to a worker (24 ms).
- After (headless 1280x720, spectate_fight, 9 runs): worst startup frame 62-76 ms (steps: colour 46-74, world map 55-97, sky 47-61,
  water 31-46, characters 5-11, detail in three frames), worst session-load frame 64-87 ms. Two of the 17 runs peaked over 100 ms once
  (startup 106 and 114, session 124): the 114 run had every step inflated 1.5-2x (the shared desktop busy); the 106 frame did a 2 ms
  step and no world CPU at all (it waits on the GPU present under the uploads). The remaining ~50-90 ms CPU frames are named: the detail
  overlay's single `sg_make_image` of an 8192^2 RGBA8 image with its full mip chain (sokol uploads a mip chain in one call, so it cannot
  be split), the world map image and the colour image; and the session load's first world frames stream the terrain tiles round the
  camera (`world_loading`), which is the load itself.
- Scripted runs still block by design: they run every load step in `init` and the first world frame waits for the towns / buildings /
  foliage workers (deterministic shots); the same `stall` events name that frame.
- Session loading screen (`begin_session_load`): no synchronous load in its world frames was left to fix (64-87 ms; the streaming of the
  terrain round the camera is the load's own work).

## Playtest (user 2026-11-07; the reference is `docs/reference/PLAYTEST.md`)

Headless tests never saw a human, and play feel is small interactions. The user plays named scenarios and writes observations into the
game; those notes are the project's record of how it plays, not the chat log. The database is `playtests/` in the repo (plain text,
diffable, greppable, versioned by git, no game-derived content); the client reads it and writes the run files, and nothing else is a
source of truth.

- **A scenario** is `playtests/<scenario>/versions.md`: a header, then one entry per version, newest first.
  ```
  # bar_lure
  title: Lured into the Hub bar
  setup: one line: the place and the situation
  look_for: what the user should watch
  metrics: bandits_targeting, crew_joined_s, bodies_down
  bead: kenshi-h2v.1

  ## v2 2026-11-07
  sim: 4f2a9c10
  client: 3f796c8c
  scenario: 7b1e55aa
  changed: what changed since v1 (one line)
  answers: v1/20261106-2100 #1, v1/20261107-0900 #2
  ```
  The coordinator adds a version when a fix for the scenario's notes lands; the hashes are the builds that version was made from and the
  scenario file's hash; `answers` names the notes it means to fix (`<version>/<yyyymmdd-hhmm> #<note>`). An optional `bead: <id>` names the
  beads feature item the playtest proves (the user's feature loop, h2v.8): it fills the `bead:` line of a store-only or recipe run (a live
  server's scenario carries its own `.kscen` header's `bead=`, which the wire's tails bring to the client), and the Scenarios window shows
  it under the selected scenario's title (`BEAD: kenshi-...`).
  A header line `run: recipe` marks a **recipe**: a game flow with no `.kscen` (the journey's New Game / Save / Reload / Load steps,
  k16.17-k16.23). Play starts a run record against the session as it runs and sends the server no `SCENARIO_LOAD` (there is no file to
  load), so the run's `sim:` is the running session's build (the wire's when this session loaded a scenario, else the client's own when it
  started the server, else `?`), its `seed:` is 0 and its `metrics:` line is empty (the header's `metrics:` is empty too:
  `SCENARIO_METRICS` needs a scenario). Leaving writes the file and sends no `SCENARIO_END`. A recipe's run keeps going through a
  NEW_GAME: the new game is the flow it records. The Scenarios list tags a recipe's row `[recipe]`, and selecting one shows the setup line
  (the recipe) in full in the window's wrapping text, above the look-for (labelled `Recipe:` and `Look for:`), since that is what the user
  plays by.
- **A run** is `playtests/<scenario>/v<N>/<yyyymmdd-hhmm>.md`, created at Play and rewritten when the notes close, on leaving and when the
  metrics arrive:
  ```
  # bar_lure v2

  date: 2026-11-07 15:30
  sim: 4f2a9c10
  client: 3f796c8c
  seed: 1302
  bead: kenshi-h2v.1
  metrics: bandits_targeting=2, crew_joined_s=6.8, bodies_down=2
  verdict: good

  ## Notes

  1. 15:42.3 Wanderer (-51011, 3419): both bandits came through the door and up the stairs.

  ## Triage

  1. no change: fixed in v2 (this run).
  ```
  One note per line; the Mark stamp starts the line (the game time as `HH:MM.S`, the selected character, its x/z). Triage is the
  coordinator's answer per note number, and a rewrite keeps it. A run on a build that differs from its version's hashes is kept and
  flagged (`mismatch`), not dropped. A run's version is the newest in versions.md when Play was pressed; its sim / client hashes are the
  builds actually running (`?` when a build is not known, as the sim's is until the wire carries it). Its `bead:` is the started scenario's
  (the `SCENARIO_STARTED` tail), else the store header's for a store-only or recipe run; no line when neither has one.
- **Client** (`src/playtest.cpp`; the windows are `src/ui/scenarios.cpp` and `src/ui/notes.cpp`; `src/ui/playtest_state.hpp` is the only
  interface between them): the store is read at start (`--playtests DIR`, default `<repo>/playtests`). The Scenarios window lists the
  scenarios and, for the selected one, its runs per version (hashes with the mismatch marked, seed, the metric columns, verdict, first
  note); PLAY starts a run. The Notes window (Ctrl+N during a run) writes the numbered notes with the verdict; MARK puts a stamp before
  the line; the sim pauses while the text is typed (the pause order, restored after).
- **Script ops** (`--debug`): `playtest list`, `select NAME`, `play [NAME]`, `note TEXT`, `verdict good|off|broken`, `mark`, `save`; the
  fixture store is `client/tests/playtest_fixture/` (bar_lure: two versions, three runs, one hash mismatch; manhunters_desert).
- **Status**: the client side (store, windows, run records, the git hash in `--help` and every run) is in. The sim side is in (task CE,
  2026-11-07): the five scenario files under `scenarios/` with their headers, and the SIMLINK wire — SCENARIO_LIST_REQ 102 / SCENARIO_LIST
  54, SCENARIO_LOAD 103 / SCENARIO_STARTED 55, SCENARIO_END 104 / SCENARIO_METRICS 56 (type numbers and fields: SIMLINK.md "SCENARIO").
  The client lists via the wire, Play sends LOAD (the server's `simHash` and `startGameTime` fill the run), and leaving sends END: the
  metrics arrive in the header's order and the run's `sim:` is no longer `?`. A metric with `valid` 0 is "not reached", written as such in
  the run's `metrics:` line. A LOAD or LIST_REQ unanswered after 15 s (an older server: real loads take <0.5 s) shows "The server did
  not answer the scenario request (older server build?)" and writes no run file (6cf27283). A recipe (the header's `run: recipe`) records
  a session's game flow with no SCENARIO_LOAD and no SCENARIO_END (k16.2.97). Input recording (a judged run replayed headless as a regression test) is later.

## Tree leaves sway (user 2026-11-03; deviation, opt-in, user to judge)

The original does not move tree leaves. A FOLIAGE_MESH `leaves mesh` (and a type-4 FOLIAGE trunk) is a StaticObject clone: the exe
forces material type 4 on a copy and sets no wind parameter (`findings/foliage_wind.md`, FUN_1406d1380; no shipped shader reads
`windFactor*`). The PagedGeometry wind batching (`Forests::WindBatchedGeometry`, the FOLIAGE_LAYER `wind` bool, 59 of 323 layers) needs a
per-record `wind` flag that no FOLIAGE_MESH has, so mesh foliage stays static in shipped data. The only wind the original animates is the
grass layer (GrassLoader per frame: phase += 0.3 pi/s of real time, `frequency` 2.0, direction +X, amplitude = GRASS `wind factor` x 3 world
units, and only the vertices whose UV.y is 0 move).

Ours sways the leaves, as the user asked, on the same wind our shrubs use (grass.glsl: the ANIM clock and direction), so both move
together: a leaves part is displaced by 5% of its mesh height at the top, weighted by the squared height fraction, so the canopy moves and
the trunk does not. Code: `BuildingPartDef::sway` (buildings.cpp, foliage.cpp set it on every leaves mesh), the mesh's top and the clock
travel to `inst_vs` (mesh.glsl) in `tile.z` and `camw.w`. Shadows move with the leaves (the shadow pass uses the same vertex shader).
It is opt-in: the cfg key `render.leaf_sway` (Bool, default off = the original's static canopy; a running client picks the edit up, no
restart). Deviation, opt-in, user to judge.
Status 2026-11-07: two shots 0.5 s apart at greenlands_bridge differ in 1923 canopy pixels with the sway against 19 without, and nothing
below the canopy changes; scene_test 33 changed / 7 pass against the drifting baseline, 0 sg errors; smoke clean.
