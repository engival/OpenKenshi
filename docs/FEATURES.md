# Feature parity checklist

**This is the code-coverage index**: what the original does and how far our sim and client cover it, one row per system.
The feature list itself (what the user plays and judges) is the beads feature items (label `feature`, the feature loop:
`~/git/kenshi/kenshi-coordinator/docs/FEATURE_LOOP.md`) and their scenarios and run records in `playtests/`.

One line per player-visible feature of the original game. Not a design doc:
detail goes in `docs/reference/`, linked from the Ref column.

Columns: **RE** = how the original does it is understood and written down,
**Sim** = works in our runtime, **Cl** = shown/usable in the client.
Marks: `x` done, `~` partial or prototype, blank = not started, `-` not applicable.

First pass 2026-10-31, marks set from `docs/history/STATUS_2026-11-02.md` and existing reference
docs; correct them as you go.

## How this list is kept complete

A decompile is too big to read top-down, but four things in the game
enumerate its features mechanically. When adding a section, sweep these:

1. **Record types** — `docs/formats/MOD_FORMAT.md` itemType table (114). Each
   type is a game system (FARM_DATA, LIMB_REPLACEMENT, TUTORIAL, ...).
2. **GUI layouts** — `data/gui/layout/*.layout` (54). Each is a screen or panel
   the player can open.
3. **Fields** — `fcs.def` field names per record type, and CONSTANTS, list the
   knobs a system has (`docs/reference/GAMEDATA_SCHEMA.md`).
4. **AI task types** — 289 `taskType` values (`docs/reference/ORIGINAL_AI.md`
   §5). Each is something a character can be told or decide to do.

Any record type, layout or task type not covered by a line below is a gap.

Player knowledge fills in behaviour: `docs/reference/community/` holds
numbers and rules from the wiki (unverified). Rows citing `community/` came
from there.
